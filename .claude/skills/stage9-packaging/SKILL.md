# 9단계 납품 정리 방법론

## 0. 방식 고르기 — 직접 정리(in-place)와 패키지(package)

프로젝트 `workspace/<project>/delivery.yaml` 의 `mode` 로 정한다(없으면 package). 사람이 정한다.

| 방식 | 언제 | 결과 |
|---|---|---|
| `in-place` | 납품 경로가 공유 브랜치 그대로이고, 필요 없는 폴더(docs·시험 등)는 받는 쪽(CICD 등)이 뺀다 | 공유 브랜치에 정리 커밋 1개. 폴더·파일은 지우지 않는다 |
| `package` | 저장소에는 개발용 근거를 남기고 납품할 때만 정리본이 필요하다 | 별도 폴더나 고아 납품 브랜치(아래 1~4절) |

### 직접 정리(in-place) 절차

실측(2026-10): 별도 납품 브랜치를 만들고 폴더까지 빼는 방식을 사람이 취소했다. 받는 쪽이 폴더를 직접 빼므로, 공유 브랜치의 소스만 정리하면 된다는 결정이었다.

1. **작업 트리**: 공유 브랜치 최신에서 새 로컬 브랜치를 딴 깨끗한 작업 트리에서 한다. 다른 변경과 섞지 않는다.
   다른 개발자에게 정리 시점을 미리 알린다. 정리 커밋은 많은 파일의 주석을 건드리므로, 진행 중 작업과 충돌할 수 있다.
2. **검사**: `python tools/package_delivery.py --target <트리> --check --rules workspace/<project>/delivery.yaml --cache <캐시> --polish-out <폴더>/polish.jsonl`.
3. **다듬기**: 미처리 대상이 있으면 `comment-polisher` 로 캐시를 채운다. DDL COMMENT 는 **컬럼 한글명과 짧은 설명만** 남긴다. 근거·경위 서술은 쓰지 않는다.
4. **적용**: `--in-place --require-polish` 로 작업 트리를 고친다. 도구는 커밋하지 않는다.
   - `exclude`·`ai_artifacts`·`passthrough` 경로는 지우지도 고치지도 않는다.
   - 문자열·코드에 금지어가 남으면 기본은 중단한다. 소스 문구를 바꾸지 않기로 했으면 `--deny-report-only` 로 보고만 하고 진행한다. 이모지는 언제나 막는다.
5. **확인**: 빌드와 단위 시험을 돌린다. 코드 불변은 도구가 증명하지만, 주석 처리기 경계 사례(문자열 속 주석 기호 등)는 빌드가 잡는다.
   `<base>.changes.txt` 를 표본 검토한다.
   - 정리 뒤 시험이 새로 실패하면 대개 주석 문구를 단언하는 시험이다. 코드 불변은 이미 증명됐으므로 시험 쪽을 정리본에 맞춘다.
   - 원문 보존·실행 여부 단언은 남기고 번호·파일:줄 단언은 뺀다. 잠긴 spec 이면 해제 → 수정 → 재잠금 순서로 한다.
   - 시험 수정은 정리 커밋과 별도 커밋으로 둔다.
6. **커밋·업로드**: 정리 전용 커밋 1개를 만든다. 공유 브랜치를 다시 받아 맞춘 뒤 push 한다. push 는 그 건마다 사람이 승인한다.
7. **공지**: 바뀐 Flyway 마이그레이션 목록을 브랜치 공지에 적는다(체크섬 변경).
   - 이미 마이그레이션한 DB(개발자 로컬, 운영 적용분이면 운영까지)는 다음 기동 전에 `flyway repair` 를 1회 실행해야 한다.
   - 다른 개발자는 정리 커밋을 받은 뒤 자기 작업을 병합한다. 주석 충돌은 정리본을 기준으로 푼다.
8. **다시 돌리기**: 이미 정리된 파일은 다시 돌려도 바뀌지 않는다. 그 뒤 생긴 흔적만 정리되므로 업로드 전마다 돌릴 수 있다.
   흔적이 다시 쌓이지 않게, 코드 주석에는 사람이 읽을 설명만 쓴다(stage2-backend §B-7).

아래 1~4절은 package 방식의 설명이다. 규칙(2절 표)·다듬기·코드 불변 검증·Flyway 목록은 두 방식이 같이 쓴다.

목표: 공유 저장소는 개발자끼리 쓰는 근거(판단·요구서·확인 항목 번호, `[의미차이:…]`, AS-IS 파일:줄 참조, 작업 문서)를 그대로 두고,
**납품할 때만** 커밋된 소스를 꺼내 고객용으로 정리한 패키지를 만든다. 코드는 한 글자도 바꾸지 않는다.

## 1. 언제 돌리나 — 8단계와 따로 두는 이유

- 5·6·7단계는 RR 을 낳고 RR 은 코드를 바꾼다. 패키지는 **검증이 끝난 고정 커밋**에서 만들어야 의미가 있다.
  순서: 기준 커밋 고정(로컬 태그) -> 5·6·7 -> RR 반영 -> 다시 고정 -> 9단계.
- 리허설(`--check`, 또는 임시 폴더로 `--out`)은 큰 업로드 뒤·시험 전에 여러 번 돌려 금지어·다듬기 대상 수의 추이를 본다(마지막에 몰리지 않게).
  리허설은 state 를 바꾸지 않는다. 최종 패키지에서만 `stages.stage9_packaging: done`.
- 8단계 산출물(정의서·결과서)은 문서를 **만드는** 일, 9단계는 납품 범위를 **정리하는** 일이다. 8단계 산출물을 납품에 넣으려면 9단계 규칙의 `keep` 에 적는다.

## 2. 정리 범위 (처음 판 - 결과를 사람이 보고 규칙을 늘린다)

| 범위 | 기본 처리 | 규칙 키 |
|---|---|---|
| 소스 주석 | 표지 지우기(번호·의미 차이·파일:줄·에이전트 용어·계정명·커밋 해시·이모지), 내용 없는 주석·줄 삭제 | `scrub`·`drop_if_only`·`accounts` |
| 긴 주석·DDL COMMENT | `comment-polisher` 가 사람이 쓴 짧은 주석으로 다듬기(캐시) | `polish` |
| 문서(md) | 기본은 전부 제외. 고객이 요구한 문서만 `keep` 으로 넣고, 넣은 문서는 통째로 다듬기(kind=doc) | `exclude`·`keep`·`polish.doc_paths` |
| AI 관련 산출물 | `.claude/`·`CLAUDE.md`·`AGENTS.md`·에이전트 결과 등은 keep·passthrough 보다 앞서 언제나 제외 | `ai_artifacts` |
| 시험 | 기본 제외. 납품하면 `keep`(납품 뒤 다른 담당이 빼면 `passthrough`) | `exclude`·`keep`·`passthrough` |

- 규칙: `config/delivery/rules.yaml`(공통), `workspace/<project>/delivery.yaml`(프로젝트 - 목록은 이어 붙인다).
  프로젝트 고유의 AI 작업 문서 폴더(파이프라인 메모·이관 작업 문서)는 프로젝트 `ai_artifacts` 에 적는다.
- 사람이 결과를 보고 "이것도 빼라·이것은 남겨라" 를 말하면 규칙으로 옮기고(프로젝트 고유면 delivery.yaml, 일반화되면 rules.yaml), 다시 만든다.
  같은 말을 두 번 듣지 않게 규칙으로 남기는 것이 목적이다.

## 3. 도구와 원칙

- 도구: `python tools/package_delivery.py --target <target_dir> --ref <고정 커밋|태그> --out <빈 폴더> [--rules workspace/<project>/delivery.yaml]`
  (`--check` 는 쓰지 않고 검사만).
- 커밋된 내용만 꺼낸다(git 이력·커밋 메시지·커밋 안 한 변경은 나가지 않는다). 소스는 **주석 구간 안만** 고치고 문자열·코드는 바꾸지 않는다.
  설명용 문자열만 있는 파일(DDL `COMMENT`)은 `scrub_strings` 로 문자열까지 고친다 - 문장 끝 `;` 같은 코드 글자는 건드리지 않는다.
  `scrub_strings` 는 DDL `COMMENT '...'` 값 안만 고친다 - 같은 파일의 INSERT 시드 값(메일 주소·화면 문구 등)은 데이터라 건드리지 않는다.
- **금지어(deny)가 문자열·코드에 남으면 패키지를 만들지 않는다(종료 코드 2).** 로그·예외 문구에 판단 번호가 들어 있으면 소스를 RR 로 고친다
  (시험이 문구를 단언할 수 있어 패키지에서 몰래 바꾸지 않는다).
- **납품 뒤 다른 담당이 빼는 경로**(예: CICD 가 옮길 때 빼는 `docs`·시험)는 `keep` + `passthrough` 로 넣는다 - 그대로 들어가고 정리·금지어 검사를 하지 않는다.
  그래도 `ai_artifacts` 는 빠진다.
- 주석에서 함께 지우는 것: git 계정명(`accounts`)과 그 앞뒤 날짜·커밋 문맥, 커밋 해시, 이모지. 계정명·이모지는 결과 어디에든 남으면 금지어다.
  이모지가 기능인 코드(이모지 정제 정규식 등)만 `deny_skip` 에 근거와 함께 적는다.
- **코드 불변 검증(종료 코드 4)**: 원본과 패키지에서 주석(SQL 은 DDL `COMMENT` 값까지)을 걷어낸 나머지가 같아야 한다. 하나라도 다르면 아무것도 쓰지 않는다.
  문서(`.md`·`.txt`·`.adoc`)는 코드가 없어 이 검증에서 뺀다. 규칙을 넓히다 데이터·코드를 건드리면 여기서 잡힌다(실측: 줄 전체 정리가 시드의 메일 주소를 바꿨다 - `docs/LESSONS.md`).
- **다듬기**: 도구가 대상(긴 DDL `COMMENT`, 근거·결정 서술 위주의 긴 블록 주석, 패키지에 남는 문서)을 골라 `<out>.polish.jsonl` 로 내보내고,
  `comment-polisher` 가 다듬은 글을 캐시(`workspace/<project>/delivery/comment-cache.jsonl`)에 덧붙인다. 다시 돌리면 `--cache` 로 적용한다.
  캐시 열쇠는 (경로, 종류, 규칙 처리 뒤 원문 해시)라 두 번째 패키징부터는 바뀐 것만 다듬는다.
  최종 패키징은 `--require-polish`(미처리 남으면 종료 코드 5)로 한다. 다듬은 글이 주석 기호를 깨거나 금지어·이모지를 품으면 적용하지 않는다(캐시 무효).
- **바뀐 Flyway 마이그레이션 목록**(`<out>.summary.json` 의 `flyway_changed`): COMMENT 정리로 체크섬이 바뀐다. 패키지로 처음 만드는 DB 는 문제없고,
  원본으로 이미 마이그레이션한 DB 에 배포하면 배포 전 `flyway repair` 1회가 필요하다 - 배포 안내에 적는다. 원본과 패키지를 같은 DB 에 번갈아 배포하지 않는다.
- **납품 브랜치**: `--branch <이름> --worktree <폴더>` 는 원본 저장소 밖 작업 트리의 고아 브랜치에 스냅샷 커밋 1개를 만든다(원본 이력과 잇지 않는다,
  `main`·`dev` 등과 기준 브랜치 이름은 거부, push 하지 않는다). 그 브랜치는 사람·AI 모두 직접 고치지 않고, 원본 -> 납품 한 방향으로만 다시 만든다.
- 확인: 패키지 폴더에서 빌드(시험 제외)를 돌리고, `<out>.changes.txt`(바뀐 주석 전부)와 남은 문서를 사람이 표본 검토한다.
  표지 규칙은 휴리스틱이라 남는 흔적·지나친 삭제가 있을 수 있다 - 발견하면 규칙을 고치고 다시 만든다.

## 4. 산출물 및 상태

- 패키지 폴더(또는 납품 브랜치 커밋), `<out>.changes.txt`·`<out>.summary.json`·`<out>.polish.jsonl`(미처리만)
- 레포트 `workspace/<project>/reports/<ts>_stage9_package.md`: 기준 커밋, 패키지 파일 수·제외 수(AI 산출물 제외 수 따로), 정리한 주석 수,
  다듬기(캐시 적용·미처리·무효, 종류별), 코드 불변 검증, 금지어 결과, 바뀐 Flyway 목록, 빌드 결과, 표본 검토 결과, 납품 브랜치 커밋(만들었으면),
  사람이 이번 회차에 준 정리 지시와 그것을 옮긴 규칙.
- pa-meta `gates`: `package_delivery.py --out …` 실행(kind `other`, 종료 코드 0), 패키지 폴더 빌드(kind `build`). 게이트가 둘 다 요구한다.
- 최종 패키지에서만 `state.yaml → stages.stage9_packaging: done`. 코드가 바뀌어(RR 반영) 다시 고정하면 `pending` 으로 되돌린다.

## 공통 금지 — 이모지 (전역 규칙 · 예외 없음)

이 방법론으로 만드는 모든 산출물(다듬은 주석·문서·레포트)에 이모지를 쓰지 않는다.
규칙 전문과 강제 장치는 `pipeline-core §15`. 이 문서의 규칙과 충돌하면 전역 규칙이 우선한다.
