# 0단계 준비 (Ingest) 방법론

목표: 이후 모든 단계가 원문 전체를 다시 읽지 않아도 되도록, 입력 자료를 **근거 링크가 달린 요약 지식**으로 바꾼다.

## 1. 입력 인벤토리

`workspace/<project>/00_inputs/` 를 재귀적으로 훑어 파일을 유형별로 분류한 표를 만든다.

| 유형 | 판별 기준 | 읽는 방법 |
|---|---|---|
| 요구사항/RFP | 파일명·제목에 요구사항, RFP, 제안요청 | 전체 정독. 요구사항에 ID 가 없으면 `REQ-<3자리>` 를 부여하고 원문 위치를 기록 |
| 분석/설계 산출물 | 화면정의서, 테이블정의서, 인터페이스정의서, ERD, 아키텍처 | 표·목록 위주로 추출 |
| **업무 규칙·공통코드** | 파일명·제목에 업무규칙, 업무정의, 코드정의, 공통코드, 상태전이, 정책, 계산 규칙 | **전체 정독**. 규칙마다 `BR-<3자리>` 를 부여하고 brief §8-1 에 **전수** 싣는다. 코드 그룹·값은 통째로 옮긴다(요약 금지 — 2단계가 seed 로 쓴다) |
| 화면 근거 | 피그마 export(png/svg/pdf), 스토리보드(pptx/pdf) | 화면 단위로 ID·이름·주요 요소·전이 관계 추출 |
| 환경 정보 | 인프라, 배포, 계정, 외부 연동 | 기술 스택·환경 표에 반영 |
| AS-IS 소스 | `asis/` 하위 코드·DDL | §3 |
| 기타 | 위에 안 맞는 것 | 목차만 읽고 관련 절만 정독 |

**Figma 원본(API 로 읽는 경우)은 한 번 볼 때 전부 저장한다** - 조회 횟수가 제한적이라 다시 들여다보지 않게 한다.
`00_inputs/figma_<이름>_<날짜>/` 에 (1) 쓰는 page 노드 JSON 원본, (2) 화면 프레임별 렌더 이미지, (3) 프레임별 전체 글자,
(4) `figma_version.json`(`GET /v1/files/<key>?depth=1` 의 version·lastModified), (5) `python tools/figma_desc_map.py --dir <폴더>` 로 만든
Description 번호 항목 ↔ 화면 번호 배지 ↔ 배지가 가리키는 컴포넌트 매핑(`desc_map/`, 컴포넌트 crop 이미지 포함)을 남긴다.
다음 조회는 version 만 먼저 보고 같으면 저장본만 쓴다. 다르면 쓰는 page 만 다시 받아 프레임별로 비교하고 바뀐 프레임만 이미지를 다시 받는다
(파일 lastModified 는 다른 쪽 수정에도 바뀐다). 매핑의 '확인' 행만 crop 이미지로 보고, Figma 배지 번호 오류는 RR·OI 근거로 적는다.

문서 형식별 읽기: pdf → 페이지 단위 읽기, docx/pptx/xlsx → 사용 가능한 스킬(docx/pptx/xlsx)로 텍스트 추출.
읽지 못한 파일은 "근거 부족" 표에 남긴다.

## 2. PROJECT_BRIEF.md 작성

`templates/PROJECT_BRIEF.md` 의 절을 그대로 채운다. 원칙:

- 모든 행에 **근거(`문서명#절` 또는 `파일경로:라인`)** 를 단다. 근거 없는 내용은 쓰지 않는다.
- 기술 스택은 `config/project.yaml → stack` 이 최우선이고, 문서와 다르면 §11 모순 항목에 적는다.
- 엔티티·화면·API 후보·요구사항 목록은 **빠짐없이** 뽑되 설명은 한 줄로. 목록이 200행을 넘으면 절별로 `workspace/<project>/knowledge/brief/<절>.md` 로 분리하고 brief 에는 요약과 링크만 둔다.
- 용어집은 문서 간 표기가 다른 용어(예: 회원/고객/사용자)를 통일한 결과를 담는다.
- **업무 규칙·공통코드 문서는 §8-1 에 전수 싣는다**(요약하지 않는다). 차세대에서 `ASIS_FUNCTION_CONTRACTS.md` 가 하던 "기대 동작의 정본" 역할을
  신규 개발에서는 이 문서가 한다 — 2단계 기대 동작 테스트(`behavior-spec-writer`)와 공통코드 seed 가 여기서만 근거를 얻는다.
  실측(신규 개발 1회차): 입력 중 가장 두꺼운 문서였고 **문서 간 상충 3건이 전부 이 문서와 요구사항 사이에서** 나왔는데, 분류표에 자리가 없어
  0단계 에이전트가 넣을 절을 스스로 만들어야 했다.
- 코드 컨벤션(§3)은 문서에 없으면 프로필 기본값(`stage2-backend/profiles/*`, `stage4-frontend/profiles/*`)을 제안값으로 적고 "제안" 표시.
  예외: **§3-1 주소·경로·이름 규칙은 프로필 기본값으로 채우지 않는다** — 결정 항목으로 올리고 사람이 정한다(§3-1).

## 3. AS-IS 분석 (mode=migration)

`asis.source_dir` 를 대상으로 `workspace/<project>/knowledge/ASIS_INVENTORY.md` 를 만든다.

1. 언어/프레임워크/빌드 도구 식별, 디렉토리 구조 요약(깊이 3).
2. 프로그램 인벤토리: 진입점(Controller/Action/JSP/서블릿/배치) 목록 — 경로, 역할 한 줄, 호출하는 테이블.
3. 테이블 인벤토리: DDL 또는 SQL 에서 테이블·주요 컬럼·관계 추출.
4. 공통 모듈: 인증, 세션, 코드 테이블, 유틸, 예외 처리, 로깅 위치.
5. 이관 리스크: 저장 프로시저, 동적 SQL, 파일 I/O, 외부 연동, 하드코딩된 설정.
6. 규모: 프로그램 수, 테이블 수, 대략의 LOC.

프로그램 수가 많으면(300개 이상) 패키지 단위로 묶어 요약하고 상세는 `workspace/<project>/knowledge/asis/<패키지>.md` 로 분리한다.

7. **기능 인벤토리 → 동작 계약** (`ASIS_FUNCTION_CONTRACTS.md`): 컨트롤러 엔드포인트·화면 템플릿(ftl/jsp)·배치 job 마다 한 행 — `입력(파라미터·세션·파일) → 호출 SQL(namespace.id 목록) → 출력(뷰 모델/JSON/파일/메일/리다이렉트) → 부수효과(DB 변경·외부 호출)`. 조건 분기(`<#if>`, 권한 분기)도 행으로. **이 표가 "기능 무손실" 의 기준**이자 5단계 특성화 시나리오의 원천이다. 근거 없는 추정은 쓰지 않고 `파일:라인`.
8. **SQL 호출 인벤토리**: `sql-migrator` 를 `inventory` 로 호출해 `ASIS_SQL_INVENTORY.md`(4분류) 를 만든다(`migration-sql` 스킬). B(호출·미정의) 는 RR(high) 로.
   statement 마다 실행 데이터소스(호출 세션)·운영 프로필 엔진·이관 판정을 적고, 데이터소스가 둘 이상이면 데이터소스 지도 `knowledge/DATASOURCES.yaml` 을 함께 만든다(pipeline-core §22).
   이관 여부(role)는 사람 확인 지점에서 보여 준다 — 특히 이관 대상과 같은 이름의 테이블을 쓰는 외부 statement, 개발·운영 엔진이 다른 데이터소스, 다른 스키마·계정 테이블을 주 DB 로 합친 것.
9. **공통 클래스 인벤토리** (`ASIS_COMMON_INVENTORY.md`): 유틸·인터셉터·필터·BaseDAO/BaseController·예외·응답·세션·설정 XML 마다 — 역할, 사용처 수, TO-BE 대응 후보(계승/대체/개선/폐기 초안 — 확정은 3단계). 설정 XML(dispatcher·context·scheduler·properties)의 빈·인터셉터·스케줄 job 목록 포함.
9-1. **실행 자원 설정 인벤토리** (`ASIS_RUNTIME_CONFIG.yaml`·`.md`).
    - 설정 XML·properties 에서 다음 **값**을 전수로 뽑는다: 스케줄러·실행기 pool-size, DB 풀(maxActive·maxWait 등), statement·socket·connect timeout, 업로드 maxUploadSize·maxInMemorySize, 세션 timeout.
    - 명령: `python tools/runtime_config.py scan --asis 00_inputs/asis [--exclude "<개발용 프로필 glob>"]`.
    - 9번의 "빈·job 목록" 만으로는 값이 빠진다. 실측: 스케줄러 pool-size 10 이 목록에 없었고, TO-BE 에서 기본값 1 로 바뀌었다.
    - 운영 프로필이 따로 있으면 운영 값을 기준으로 남기고, 개발용 프로필은 제외한다.
    - 판정은 2·3단계가 한다(stage2-backend §B-9, 게이트 `runtime-config`).
10. **범위 원칙**: 들어온 소스가 곧 범위. TO-BE 배경 정보(신규 기능·배포·서버)는 §2 환경과 §12 변환 규칙의 근거로만 쓰고, 해당 AS-IS 소스가 없는 항목은 brief §1 에 "범위 외(소스 미입력)" 로 명시한다.

## 3-1. 주소·경로·이름 규칙 — 1단계 전에 사람이 정한다 (pipeline-core §25)

화면 주소(프론트 라우트)·메뉴 주소·API 경로·패키지와 파일 배치는 **slice 를 나누기 전에** 한 번 정한다. 정하지 않으면 slice 마다
developer 가 따로 정하고, 프로필 기본값(`/<slice>/...`)이 조용히 쓰여 파이프라인 내부 이름(slice id)이 사용자 주소로 새어 나간다(실측).
API 경로는 2단계 골격이 바로 써야 해서 정해지지만, 화면 주소는 4단계까지 아무도 묻지 않는다 — 그래서 0단계가 결정 항목으로 올린다.

### (brownfield) target_dir 에 기존 코드가 있으면 — 기존 TO-BE 규약 추출

파이프라인 밖에서 만든 코드(앞 차수 TO-BE)가 target_dir 에 있으면 **그 코드의 관례가 1차 정본**이다. 실측해서
`workspace/<project>/knowledge/TOBE_CONVENTIONS.md` 에 표로 뽑는다. 문서·기억이 아니라 소스에서 센다(행마다 `파일:라인`).

| 표 | 무엇을 뽑나 | 어디서 |
|---|---|---|
| 화면 라우트 | 앱(사용자·관리)별 라우트 주소 전수, 주소 모양(`/<메뉴 영역>/<업무>`, 관리 화면 `/<영역>/manage/<업무>` 같은 패턴), 경로 변수 표기, 라우트 정의 위치(파일·상수) | 라우터 설정·라우트 상수·`routes.*` |
| 메뉴 데이터 | 메뉴 테이블·시드의 주소 컬럼(`menu_uri` 류) 값 전수와 라우트와의 대응(같은가·다른가), 메뉴 트리 경로 | 마이그레이션·시드 SQL, 메뉴 관리 코드 |
| API 경로 | 접두(`/api/v1` 등), 모듈별 구분, 자원 이름 규칙(단수·복수·케밥), 행위 경로 | 컨트롤러 매핑 |
| 패키지·파일 배치 | 백엔드 패키지 규칙, 프론트 기능 폴더 규칙, 공용 위치 | 디렉터리 구조(깊이 3~4) |
| 이름 | 화면 ID·메뉴 ID·컴포넌트·Mapper 이름 규칙 | 위 소스 |

- 패턴은 **건수와 예외**를 함께 적는다("라우트 42개 중 40개가 `/<영역>/<업무>`, 예외 2개: …"). 예외를 규칙으로 삼지 않는다.
- (migration) AS-IS URL 목록(`ASIS_FUNCTION_CONTRACTS.md` 의 진입점 경로)을 같은 문서에 두고, 기존 TO-BE 가 이미 옮긴 화면은 "AS-IS URL -> TO-BE 주소" 대응을 실측으로 적는다.
  이번 차수 화면이 같은 패턴으로 어떤 주소가 될지는 1단계가 정한다 — 0단계는 규칙만 정한다.

### 결정 항목으로 올린다 — brownfield·신규 개발 공통

`python tools/gate.py oi new --stage 0 --kind decision --severity high --summary "화면 주소·API 경로·이름 규칙 결정" --evidence "knowledge/TOBE_CONVENTIONS.md" --target 0`
으로 채번하고, 본문(레포트·brief §11)에 **추천안 하나와 대안**을 장단점과 함께 적는다.

- brownfield: 추천안은 보통 "기존 TO-BE 관례를 그대로 따른다" 다. 기존 관례와 다르게 가야 할 근거(요구사항·화면 설계)가 있으면 대안으로 올리고, 종전 주소를 바꾸면 흡수 라우트(리다이렉트)가 필요하다는 영향을 적는다.
- 신규 개발: 기존 코드가 없으므로 화면 설계서·메뉴 구조(스토리보드의 메뉴 트리)에서 추천안을 만들고 결정 항목으로만 올린다. 프로필 기본값을 결정으로 쓰지 않는다.
- 규칙에 담을 것: 사용자·관리 화면 주소 패턴, 메뉴 주소와 화면 주소의 관계(같게 쓴다가 기본), 경로 변수 표기, API 접두·자원 이름, 화면 ID 규칙. **slice id 는 주소에 쓰지 않는다**(내부 이름이라 업무명과 다르고 다음 재분류에서 바뀐다).
- 사람이 정하면 brief **§3-1 주소·경로·이름 규칙**에 적고 §12 에 결정으로 기록한다(판단 기록 JD 연결, `oi set <id> resolved --jd JD-xxxx`).
  **1단계는 이 결정 없이 승인 요청을 하지 않는다** — slice 마다 `routes` 를 이 규칙으로 정해 함께 승인받기 때문이다(stage1-slicing §2-2).

## 4. 근거 부족·모순 (§11)

- 문서 간 충돌(예: 화면정의서에는 있는데 요구사항에 없는 화면), 누락(엔티티는 있는데 테이블 정의가 없음), 읽지 못한 파일을 표로 남긴다.
- **kind 를 구분해 채번한다** (`pipeline-core §11`): 받은 문서에 **없는** 것은 `evidence_gap`, 문서 **둘이 서로 다른** 것은 `contradiction`,
  문서는 멀쩡한데 **사람이 골라야** 하는 것은 `decision`. 해소 경로가 달라서다 — 없는 것은 발주처에 받아야 하고(기다림),
  다른 것은 어느 쪽이 정본인지 정하면 바로 진행된다(결정). 섞으면 "지금 결정하면 풀리는 것" 이 "기다려야 하는 것" 사이에 묻힌다.
- **상충은 어느 쪽이 맞는지 정하지 않는다.** 양쪽 원문·근거와 각각을 택했을 때의 영향(테이블·API·금액 계산이 어떻게 달라지나)을 적어 올린다.
  정하는 것은 사람이고, 기록은 판단(JD)으로 남는다.
- 사용자에게 이 표를 보여주고 확인을 요청한다. 답을 기다리지 않고 stage0 는 `done` 처리하되, 항목은 brief 에 남아 1단계 이후에 참조된다.

### "근거 없음" 으로 적기 전에 두 가지를 먼저 한다 (실측 교훈)

0. **(mode: greenfield) 대조는 문서끼리 한다.** AS-IS 소스가 없으므로 "요구사항 ID <-> 화면 <-> 엔티티 <-> 업무 규칙(BR) <-> 공통코드" 를
   네 방향으로 교차 대조한다. 한쪽에만 있는 것이 모순 후보다 — 화면에만 있는 기능, 업무 규칙에만 있는 상태, 요구사항에만 있는 엔티티,
   어느 요구사항도 쓰지 않는 코드 그룹. 아래 1·2 의 표기 변형 규칙은 **문서끼리의 대조에도 그대로** 적용한다
   (같은 개념을 요구사항은 한글 업무어로, 데이터모델은 영문 컬럼명으로 쓴다).
1. **이름 대조는 한 가지 표기로 하지 않는다.** 문서는 한글명을, 소스는 영문·약어를 쓴다.
   한글명·영문명·약어·표기 변형(제/재, 띄어쓰기, 하이픈/언더바)을 모두 시도한 뒤에 "0건" 이라고 적는다.
   실측: 외부 시스템 18개 중 **7개를 "매칭 0건"** 으로 적었는데, 영문·약어로 다시 찾으니 **1개**만 남았다.
   틀린 유형 네 가지였다 — 문서는 영문 풀네임인데 소스는 **약어**(`SomeGateway` -> `sgw`),
   문서는 한글명인데 소스는 **영문 약어**(`한국XX인증` -> 그 영문 약어), 문서는 한글 복합어인데 소스는 **그 일부**,
   그리고 **동음이표기**(문서 `전자결제` -> 소스 `전자결재`).
2. **도구가 내용을 자르면 같은 파일을 다른 도구로 다시 읽어 본다.** 표 셀·긴 문단은 읽기 도구마다 잘리는 지점이 다르다.
   실측: 시트 읽기가 긴 셀을 `파…` 에서 잘라 항목 2개를 몰랐는데, **전문 검색의 스니펫**이 같은 셀 전체를 냈다.
   "도구 표본 한계" 로 확인 필요 항목을 만들기 전에 다른 경로를 시도한다.

둘 다 **거짓 근거 부족**을 만든다 — 실제로는 근거가 있는데 없다고 적으면 그 slice 가 불필요하게 `hold` 되고,
사람에게 answer 할 필요 없는 질문을 보내게 된다.

## 6. 갱신 모드 — 차수 추가·요구사항 변경

brief 가 이미 있는데 `/stage0` 를 다시 돌리는 경우다. 대표 상황은 두 가지다.
(1) 운영 중인 프로젝트에 **다음 차수 범위**(예: 3차 오픈)가 들어온 경우, (2) 같은 차수 안에서 **요구사항정의서 개정판**이 들어온 경우.
처음부터 다시 요약하면 이미 `done` 인 slice 의 근거 ID 가 바뀌어 추적 체인(요구사항 ↔ slice ↔ API ↔ 테스트)이 끊긴다. 그래서 갱신은 **대조**로 한다.

1. **입력 배치**: 새 차수 문서는 `workspace/<project>/00_inputs/<차수>/`(예: `phase3/`)에 둔다. 개정판은 기존 파일을 덮어쓰지 않고 판 번호가 붙은 새 파일로 둔다.
   어느 파일이 최신판인지는 파일명의 판 번호·날짜로 판정하고, 판정 근거를 `INPUT_INVENTORY.md` 에 적는다. 판정할 수 없으면 사용자에게 묻는다.
   (내부용·고객전달용처럼 같은 날짜의 판이 여럿이면 어느 것이 기준인지 사용자에게 확인한다 — 추측하지 않는다.)
   **같은 문서의 계열이 둘 이상이면(예: `v1.2_<날짜>` 와 `<더 이른 날짜>(내부용)`) 이름의 판 번호·날짜로 정하지 않는다** — 날짜를 고치지 않고 계속 갱신하는
   작업본이 있다(실측: 이름상 더 새 v1.2 가 실제로는 더 낡은 판이었다). 시트별 셀 비교 결과를 보여 주고 정본을 사람에게 확인한다.
   확인 전에는 기존 정본을 유지하고, 새 판 기준의 범위 변경(요구사항 삭제·번호 변경)을 slice·코드에 넣지 않는다.
2. **ID 보존**: 기존 brief §8 의 요구사항 ID 는 바꾸지 않는다. 새 요구사항은 기존 최대 번호 다음부터 부여하고, 원문에 ID 가 있으면 원문 ID 를 쓴다.
   brief §8 의 `차수` 칸에 차수를 적는다(기존 행은 비어 있으면 최초 차수로 채운다).
3. **대조표 `SCOPE_DELTA.md`**: 요구사항 한 건당 한 행.

   | 열 | 규칙 |
   |---|---|
   | 요구사항 ID | 기존 ID 또는 새 ID |
   | 구분 | `신규` \| `변경` \| `삭제` \| `유지` |
   | 이전 근거 / 새 근거 | 두 판의 `문서명#절` (신규는 새 근거만, 삭제는 이전 근거만) |
   | 차이 요약 | 무엇이 바뀌었는가 한 줄. `유지` 는 비운다 |
   | 영향 slice | `slices.yaml` 의 id. 신규라 아직 없으면 `미배정` |
   | 영향 slice 상태 | 그 slice 의 stage2·stage4 상태 (state.yaml 실측) |

   화면·엔티티·API 후보도 바뀌었으면 같은 형식의 절을 이어서 둔다.
4. **이미 만든 것에 닿는 변경은 확인 필요 항목으로 남긴다**: `변경`·`삭제` 인데 영향 slice 의 stage2 또는 stage4 가 `done` 이면
   `python tools/gate.py oi new --stage 0 --slice <id> --kind deferred --severity high --summary "<ID> 변경 반영 필요" --evidence "<새 근거>" --target 2`
   로 채번한다. 0단계는 코드를 고치지 않는다 — 반영은 `/rerun slice:<id>` 가 한다. (RR 은 이미 있는 코드의 결함이지 요구 변경이 아니므로 만들지 않는다.)
5. **brief 반영**: §5~§8 에 신규 행을 추가하고, 변경 행은 내용을 고치되 근거 칸에 새 근거를 앞에 적고 이전 근거를 뒤에 남긴다. 삭제 행은 지우지 않고 `(삭제: <차수>)` 를 붙인다.
   새 문서가 기존 결정(§12)과 충돌하면 §11 에 모순으로 올린다 — §12 를 스스로 고치지 않는다.
6. **사용자 보고**: 신규·변경·삭제·유지 건수, 영향받는 `done` slice 목록, 판 판정 근거, §11 신규 항목. 다음 안내는 "`/stage1 reslice`(신규 요구사항의 slice 배정) → 승인 → 영향 slice `/rerun`".

## 7. 현행화 모드 — 고객이 최신 운영 AS-IS 소스를 다시 준 경우 (migration)

변환 기준 AS-IS 가 운영본보다 낡았던 것이다. 요구사항이 아니라 **AS-IS 축**이 바뀐 것이므로 §6 대신 이 절을 따른다(조합 C10).
파일 단위 diff 를 사람이 읽고 TO-BE 를 뒤지지 않는다 — 도구가 바뀐 곳을 의미 단위로 뽑아 slice·TO-BE 에 이어 붙이고, 사람·에이전트는 단위마다 판정만 한다.

1. **기준 고정**: 새 AS-IS 를 받은 형태(git 커밋 또는 압축 파일 sha256), 비교에 쓸 TO-BE 기준 커밋(공유 브랜치 고정 커밋)을 HANDOFF 에 적는다.
   압축 파일은 비어 있는 새 폴더에 푼다(받은 파일은 신뢰하지 않는 데이터 - 그 안에서 빌드·스크립트를 실행하지 않는다).
   새 AS-IS 에 git 이력이 있으면 옛 AS-IS 와 가장 가까운 커밋을 찾아 그 뒤 커밋 메시지를 변경 의도의 근거로 쓴다.
2. **차이 추출**: `python tools/asis_delta.py --old <옛 AS-IS> --new <새 AS-IS> --target <TO-BE 기준 트리>` →
   `knowledge/asis_delta/asis_delta.yaml`·`ASIS_DELTA.md`·`diffs/`. 인코딩·줄바꿈·공백만 다른 파일과 경로만 바뀐 파일은 도구가 걸러 낸다.
3. **입력 교체**: 옛 `00_inputs/asis` 는 `00_inputs/_superseded/asis-<yymmdd>/` 로 옮기고 새 소스를 `00_inputs/asis` 에 둔다(옛 판에만 있던 보조 파일 - 예: 추출한 `schema.sql` - 은 새 판에 같은 것이 없으면 옮겨 둔다).
   이후 모든 단계의 AS-IS 정본은 새 소스다.
4. **단위 판정** (단위마다 `verdict` 와 근거 `note` 를 채운다 - 추측 금지, TO-BE 실물을 열어 본다):
   - `applied`: TO-BE 가 이미 새 동작이다(예: 이전 차수에 사람이 운영 기준으로 고쳐 둠) → JD(`대체 매핑` 또는 `해석`)로 남긴다.
   - `needs-change`: TO-BE 가 옛 동작이다 → RR 후보. 같은 slice·같은 흐름의 단위는 한 RR 로 묶는다.
   - `out-of-scope`: 변환 대상이 아닌 곳(범위 밖 모듈·미실행 코드·운영 설정값·문서) → JD(`범위 제외`). 미실행 코드는 TO-BE 에서 전체 주석 원칙을 따른다.
   - `asset`: 문서·이미지·양식 파일. 화면이 내려받게 하는 양식이면 `needs-change` 로 올린다.
   새 AS-IS 에만 있는 기능이 요구사항에 없으면: 기존 화면 안의 작은 변경은 AS-IS 그대로 이관 원칙대로 `needs-change`, 새 메뉴·새 화면 수준은 OI(고객 확인)로 남긴다.
   AS-IS 에서 삭제된 기능은 TO-BE 에서도 동작을 없애고(코드는 전체 주석), 고객 확인이 필요하면 OI 로 둔다.
5. **산출**: 판정 결과는 `python tools/asis_delta.py set <AD...> --verdict <판정> --note "<근거>"` 로 `asis_delta.yaml` 에 쓴다(손으로 고치지 않는다 - 다시 생성해도 (파일, 단위) 기준으로 이어받는다). 그리고 `reports/<ts>_asis_refresh_stage0.md` 에 slice 별 건수·RR 후보 묶음·OI·JD 목록을 적는다.
   인벤토리(`ASIS_INVENTORY`·`ASIS_SQL_INVENTORY`·`ASIS_FUNCTION_CONTRACTS`·`DATASOURCES.yaml`)에서 바뀐 항목만 갱신한다.
6. **다음**: 공통 단위가 있으면 `common_usage.py` 재집계 → `common_contract.py init --dry-run` 으로 공통 계약 차이 확인 → 승인 → common-porter(CR).
   업무 단위는 RR(`source_stage: 0`, 제목 앞 `[현행화]`, 근거에 `AD-NNNN` 단위 ID)로 만들어 `/refactor` 로 반영한다 - 기대 동작이 바뀌므로 **spec 개정(잠금 해제 → spec-writer → 재잠금)이 developer 보다 먼저**다.
   slice 전체 `/rerun` 은 한 slice 의 바뀐 단위가 많아 부분 반영이 더 위험할 때만 쓴다. 반영된 slice 는 `/refactor` 규칙대로 5단계를 다시 돈다.
