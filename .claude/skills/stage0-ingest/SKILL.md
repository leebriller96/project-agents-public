# 0단계 준비 (Ingest) 방법론

목표: 이후 모든 단계가 원문 전체를 다시 읽지 않아도 되도록, 입력 자료를 **근거 링크가 달린 요약 지식**으로 바꾼다.

## 1. 입력 인벤토리

`workspace/<project>/00_inputs/` 를 재귀적으로 훑어 파일을 유형별로 분류한 표를 만든다.

| 유형 | 판별 기준 | 읽는 방법 |
|---|---|---|
| 요구사항/RFP | 파일명·제목에 요구사항, RFP, 제안요청 | 전체 정독. 요구사항에 ID 가 없으면 `REQ-<3자리>` 를 부여하고 원문 위치를 기록 |
| 분석/설계 산출물 | 화면정의서, 테이블정의서, 인터페이스정의서, ERD, 아키텍처 | 표·목록 위주로 추출 |
| 화면 근거 | 피그마 export(png/svg/pdf), 스토리보드(pptx/pdf) | 화면 단위로 ID·이름·주요 요소·전이 관계 추출 |
| 환경 정보 | 인프라, 배포, 계정, 외부 연동 | 기술 스택·환경 표에 반영 |
| AS-IS 소스 | `asis/` 하위 코드·DDL | §3 |
| 기타 | 위에 안 맞는 것 | 목차만 읽고 관련 절만 정독 |

문서 형식별 읽기: pdf → 페이지 단위 읽기, docx/pptx/xlsx → 사용 가능한 스킬(docx/pptx/xlsx)로 텍스트 추출.
읽지 못한 파일은 "근거 부족" 표에 남긴다.

## 2. PROJECT_BRIEF.md 작성

`templates/PROJECT_BRIEF.md` 의 절을 그대로 채운다. 원칙:

- 모든 행에 **근거(`문서명#절` 또는 `파일경로:라인`)** 를 단다. 근거 없는 내용은 쓰지 않는다.
- 기술 스택은 `config/project.yaml → stack` 이 최우선이고, 문서와 다르면 §11 모순 항목에 적는다.
- 엔티티·화면·API 후보·요구사항 목록은 **빠짐없이** 뽑되 설명은 한 줄로. 목록이 200행을 넘으면 절별로 `workspace/<project>/knowledge/brief/<절>.md` 로 분리하고 brief 에는 요약과 링크만 둔다.
- 용어집은 문서 간 표기가 다른 용어(예: 회원/고객/사용자)를 통일한 결과를 담는다.
- 코드 컨벤션(§3)은 문서에 없으면 프로필 기본값(`stage2-backend/profiles/*`, `stage4-frontend/profiles/*`)을 제안값으로 적고 "제안" 표시.

## 3. AS-IS 분석 (mode=migration)

`asis.source_dir` 를 대상으로 `workspace/<project>/knowledge/ASIS_INVENTORY.md` 를 만든다.

1. 언어/프레임워크/빌드 도구 식별, 디렉토리 구조 요약(깊이 3).
2. 프로그램 인벤토리: 진입점(Controller/Action/JSP/서블릿/배치) 목록 — 경로, 역할 한 줄, 호출하는 테이블.
3. 테이블 인벤토리: DDL 또는 SQL 에서 테이블·주요 컬럼·관계 추출.
4. 공통 모듈: 인증, 세션, 코드 테이블, 유틸, 예외 처리, 로깅 위치.
5. 이관 리스크: 저장 프로시저, 동적 SQL, 파일 I/O, 외부 연동, 하드코딩된 설정.
6. 규모: 프로그램 수, 테이블 수, 대략의 LOC.

프로그램 수가 많으면(300개 이상) 패키지 단위로 묶어 요약하고 상세는 `workspace/<project>/knowledge/asis/<패키지>.md` 로 분리한다.

7. **기능 인벤토리 → 동작 계약** (`ASIS_FUNCTION_CONTRACTS.md`): 컨트롤러 엔드포인트·화면 템플릿(ftl/jsp)·배치 job 마다 한 행 — `입력(파라미터·세션·파일) → 호출 SQL(namespace.id 목록) → 출력(뷰 모델/JSON/파일/메일/리다이렉트) → 부수효과(DB 변경·외부 호출)`. 조건 분기(`<#if>`, 권한 분기)도 행으로. **이 표가 "기능 무손실" 의 기준**이자 5단계 특성화 시나리오의 원천이다. 근거 없는 추정은 쓰지 않고 `파일:라인`.
8. **SQL 호출 인벤토리**: `sql-migrator` 를 `inventory` 로 호출해 `ASIS_SQL_INVENTORY.md`(4분류) 를 만든다(`migration-sql` 스킬). B(호출·미정의) 는 RR(high) 로.
   statement 마다 실행 데이터소스(호출 세션)·운영 프로필 엔진·이관 판정을 적고, 데이터소스가 둘 이상이면 데이터소스 지도 `knowledge/DATASOURCES.yaml` 을 함께 만든다(pipeline-core §22).
   이관 여부(role)는 사람 확인 지점에서 보여 준다 — 특히 이관 대상과 같은 이름의 테이블을 쓰는 외부 statement, 개발·운영 엔진이 다른 데이터소스, 다른 스키마·계정 테이블을 주 DB 로 합친 것.
9. **공통 클래스 인벤토리** (`ASIS_COMMON_INVENTORY.md`): 유틸·인터셉터·필터·BaseDAO/BaseController·예외·응답·세션·설정 XML 마다 — 역할, 사용처 수, TO-BE 대응 후보(계승/대체/개선/폐기 초안 — 확정은 3단계). 설정 XML(dispatcher·context·scheduler·properties)의 빈·인터셉터·스케줄 job 목록 포함.
10. **범위 원칙**: 들어온 소스가 곧 범위. TO-BE 배경 정보(신규 기능·배포·서버)는 §2 환경과 §12 변환 규칙의 근거로만 쓰고, 해당 AS-IS 소스가 없는 항목은 brief §1 에 "범위 외(소스 미입력)" 로 명시한다.

## 4. 근거 부족·모순 (§11)

- 문서 간 충돌(예: 화면정의서에는 있는데 요구사항에 없는 화면), 누락(엔티티는 있는데 테이블 정의가 없음), 읽지 못한 파일을 표로 남긴다.
- 사용자에게 이 표를 보여주고 확인을 요청한다. 답을 기다리지 않고 stage0 는 `done` 처리하되, 항목은 brief 에 남아 1단계 이후에 참조된다.

### "근거 없음" 으로 적기 전에 두 가지를 먼저 한다 (실측 교훈)

1. **이름 대조는 한 가지 표기로 하지 않는다.** 문서는 한글명을, 소스는 영문·약어를 쓴다.
   한글명·영문명·약어·표기 변형(제/재, 띄어쓰기, 하이픈/언더바)을 모두 시도한 뒤에 "0건" 이라고 적는다.
   실측: 외부 시스템 18개 중 **7개를 "매칭 0건"** 으로 적었는데, 영문·약어로 다시 찾으니 **1개**만 남았다.
   틀린 유형 네 가지였다 — 문서는 영문 풀네임인데 소스는 **약어**(`SomeGateway` -> `sgw`),
   문서는 한글명인데 소스는 **영문 약어**(`한국XX인증` -> 그 영문 약어), 문서는 한글 복합어인데 소스는 **그 일부**,
   그리고 **동음이표기**(문서 `전자결제` -> 소스 `전자결재`).
2. **도구가 내용을 자르면 같은 파일을 다른 도구로 다시 읽어 본다.** 표 셀·긴 문단은 읽기 도구마다 잘리는 지점이 다르다.
   실측: 시트 읽기가 긴 셀을 `파…` 에서 잘라 항목 2개를 몰랐는데, **전문 검색의 스니펫**이 같은 셀 전체를 냈다.
   "도구 표본 한계" 로 확인 필요 항목을 만들기 전에 다른 경로를 시도한다.

둘 다 **거짓 근거 부족**을 만든다 — 실제로는 근거가 있는데 없다고 적으면 그 slice 가 불필요하게 `hold` 되고,
사람에게 answer 할 필요 없는 질문을 보내게 된다.

## 6. 갱신 모드 — 차수 추가·요구사항 변경

brief 가 이미 있는데 `/stage0` 를 다시 돌리는 경우다. 대표 상황은 두 가지다.
(1) 운영 중인 프로젝트에 **다음 차수 범위**(예: 3차 오픈)가 들어온 경우, (2) 같은 차수 안에서 **요구사항정의서 개정판**이 들어온 경우.
처음부터 다시 요약하면 이미 `done` 인 slice 의 근거 ID 가 바뀌어 추적 체인(요구사항 ↔ slice ↔ API ↔ 테스트)이 끊긴다. 그래서 갱신은 **대조**로 한다.

1. **입력 배치**: 새 차수 문서는 `workspace/<project>/00_inputs/<차수>/`(예: `phase3/`)에 둔다. 개정판은 기존 파일을 덮어쓰지 않고 판 번호가 붙은 새 파일로 둔다.
   어느 파일이 최신판인지는 파일명의 판 번호·날짜로 판정하고, 판정 근거를 `INPUT_INVENTORY.md` 에 적는다. 판정할 수 없으면 사용자에게 묻는다.
   (내부용·고객전달용처럼 같은 날짜의 판이 여럿이면 어느 것이 기준인지 사용자에게 확인한다 — 추측하지 않는다.)
   **같은 문서의 계열이 둘 이상이면(예: `v1.2_<날짜>` 와 `<더 이른 날짜>(내부용)`) 이름의 판 번호·날짜로 정하지 않는다** — 날짜를 고치지 않고 계속 갱신하는
   작업본이 있다(실측: 이름상 더 새 v1.2 가 실제로는 더 낡은 판이었다). 시트별 셀 비교 결과를 보여 주고 정본을 사람에게 확인한다.
   확인 전에는 기존 정본을 유지하고, 새 판 기준의 범위 변경(요구사항 삭제·번호 변경)을 slice·코드에 넣지 않는다.
2. **ID 보존**: 기존 brief §8 의 요구사항 ID 는 바꾸지 않는다. 새 요구사항은 기존 최대 번호 다음부터 부여하고, 원문에 ID 가 있으면 원문 ID 를 쓴다.
   brief §8 의 `차수` 칸에 차수를 적는다(기존 행은 비어 있으면 최초 차수로 채운다).
3. **대조표 `SCOPE_DELTA.md`**: 요구사항 한 건당 한 행.

   | 열 | 규칙 |
   |---|---|
   | 요구사항 ID | 기존 ID 또는 새 ID |
   | 구분 | `신규` \| `변경` \| `삭제` \| `유지` |
   | 이전 근거 / 새 근거 | 두 판의 `문서명#절` (신규는 새 근거만, 삭제는 이전 근거만) |
   | 차이 요약 | 무엇이 바뀌었는가 한 줄. `유지` 는 비운다 |
   | 영향 slice | `slices.yaml` 의 id. 신규라 아직 없으면 `미배정` |
   | 영향 slice 상태 | 그 slice 의 stage2·stage4 상태 (state.yaml 실측) |

   화면·엔티티·API 후보도 바뀌었으면 같은 형식의 절을 이어서 둔다.
4. **이미 만든 것에 닿는 변경은 확인 필요 항목으로 남긴다**: `변경`·`삭제` 인데 영향 slice 의 stage2 또는 stage4 가 `done` 이면
   `python tools/gate.py oi new --stage 0 --slice <id> --kind deferred --severity high --summary "<ID> 변경 반영 필요" --evidence "<새 근거>" --target 2`
   로 채번한다. 0단계는 코드를 고치지 않는다 — 반영은 `/rerun slice:<id>` 가 한다. (RR 은 이미 있는 코드의 결함이지 요구 변경이 아니므로 만들지 않는다.)
5. **brief 반영**: §5~§8 에 신규 행을 추가하고, 변경 행은 내용을 고치되 근거 칸에 새 근거를 앞에 적고 이전 근거를 뒤에 남긴다. 삭제 행은 지우지 않고 `(삭제: <차수>)` 를 붙인다.
   새 문서가 기존 결정(§12)과 충돌하면 §11 에 모순으로 올린다 — §12 를 스스로 고치지 않는다.
6. **사용자 보고**: 신규·변경·삭제·유지 건수, 영향받는 `done` slice 목록, 판 판정 근거, §11 신규 항목. 다음 안내는 "`/stage1 reslice`(신규 요구사항의 slice 배정) → 승인 → 영향 slice `/rerun`".

## 공통 금지 — 이모지 (전역 규칙 · 예외 없음)

이 방법론으로 만드는 모든 산출물(소스 주석·로그 문구·Mapper 쿼리 주석·yml 주석·DDL `COMMENT`·테스트 이름·레포트·매핑표)에 이모지를 쓰지 않는다.
규칙 전문과 강제 장치는 `pipeline-core §15`. 이 문서의 규칙과 충돌하면 전역 규칙이 우선한다.
